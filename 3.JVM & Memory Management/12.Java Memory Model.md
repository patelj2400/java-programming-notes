# Java Memory Model (JMM)

The **Java Memory Model (JMM)** defines:

- ✅ How Java threads interact through memory

- ✅ How and when changes made by one thread become visible to others

- ✅ Rules for ordering and visibility of variables

It is part of the **Java specification**.

> The Java Memory Model (JMM) defines how threads interact through memory in Java and ensures visibility, ordering, and atomicity of shared data.

---

## 1.Why Do We Need Java Memory Model?

In single-thread programs → everything runs sequentially.

In multithreaded programs:

- Multiple threads share memory
- CPU may reorder instructions
- Each thread may cache variables
- Changes may not be immediately visible

✔ Each thread has its own working memory (CPU cache).
✔ Shared variables are stored in main memory (Heap).
✔ Without rules → inconsistent or unexpected results.

JMM ensures:

- Memory visibility - Correct visibility between threads

- Ordering guarantees - Proper ordering of operations

- Atomicity rules - Predictable behavior in concurrent programs

## 3.Core Concepts of JMM

#### 🔹 1. Visibility

Problem: One thread updates a variable, but other threads can't see it.

    boolean flag = false;

    Thread 1:
    flag = true;

    Thread 2:
    while(!flag) {
    // infinite loop?
    }

Thread 2 may never see the updated value.

#### ✅ Solution → `volatile`

volatile boolean flag = false;

`volatile` ensures:

- Changes are immediately visible
- No caching allowed
- Prevents instruction reordering.
- Stored directly in main memory.

---

#### 🔹 2. Happens-Before Rule

Very important for interviews 🔥

    If A happens-before B → then
    All changes in A are visible to B.
    Execution order is guaranteed

Examples:

- Thread start

- Thread join

- Lock release → lock acquire

- Writing to volatile → reading same volatile

Example:

- Thread start → happens-before its execution

- Unlock → happens-before next lock

- Write to volatile → happens-before read

---

#### 🔹 3. Reordering

Compiler and CPU may reorder instructions for optimization.

Example:

    int a = 10;
    int b = 20;

Execution order may change internally.

But JMM ensures:

- Reordering doesn't break single-thread behavior

- Happens-before rules maintain correctness

---

#### 🔹 4. Atomicity

Some operations are atomic:

- Reading/writing primitive types (except long/double pre-Java 5)
- Reference assignment
- For atomic operations use:
  - `synchronized`

  - `AtomicInteger`

  - `Lock`

Not atomic:

    count++;

It is:

1.  Read

2.  Increment

3.  Write

Solution:

- `synchronized`

- `AtomicInteger`

---

## 4.`synchronized` and Memory Model

> Two threads modify the same variable simultaneously.

When you use:

    synchronized(lock) {
        // critical section
    }

Example:

    synchronized void method() {
    // critical section
    }

`synchronized`

- Ensures mutual exclusion.

- Guarantees visibility.

- Uses monitor lock.

JMM guarantees:

- Flush thread memory to main memory

- Visibility after lock release

- Mutual exclusion

---

## 5.volatile vs synchronized

| Feature     | volatile | synchronized |
| ----------- | -------- | ------------ |
| Visibility  | ✅ Yes   | ✅ Yes       |
| Atomicity   | ❌ No    | ✅ Yes       |
| Locking     | ❌ No    | ✅ Yes       |
| Performance | Faster   | Slower       |

## 6.Real World Example

Banking system:

    class Account {
        private int balance = 1000;
        public void withdraw(int amount) {
            balance = balance - amount;
        }

    }

Two threads withdraw simultaneously → incorrect balance.

Correct:

    public synchronized void withdraw(int amount) {
        balance = balance - amount;
    }

## 9.Final Understanding

Java Memory Model ensures:

✔ Thread safety\
✔ Visibility guarantees\
✔ Order guarantees\
✔ Predictable multithreading

Without JMM → concurrency in Java would be unsafe.

- Java is **pass-by-value**, but JMM controls thread memory interaction.
- `volatile` does NOT provide atomicity.
- `synchronized` provides atomicity + visibility.
- Double-checked locking requires `volatile`.

## 8.JMM Interview Questions

##### Q1: What is Java Memory Model (JMM)?

👉 The **Java Memory Model (JMM)** defines how threads interact through memory in **Java** --- it specifies rules for visibility, ordering, and atomicity of shared variables.

---

##### Q2: Difference between Stack and Heap?

👉 **Stack:**

- Stores method calls & local variables

- Thread-specific

- Fast access

👉 **Heap:**

- Stores objects

- Shared between threads

- Managed by Garbage Collector

---

##### Q3: What is happens-before rule?

👉 It is a rule in JMM that guarantees **memory visibility** --- if one action happens-before another, the first action's changes are visible to the second.

---

##### Q4: What does `volatile` guarantee?

👉 `volatile` guarantees:

- Visibility (latest value is always read from main memory)

- No instruction reordering

❌ It does NOT guarantee atomicity.

---

##### Q5: Why is `count++` not thread-safe?

👉 Because `count++` is 3 steps:

1.  Read

2.  Increment

3.  Write

Multiple threads can interleave these steps → race condition.

---

##### Q6: Can `volatile` replace `synchronized`?

👉 ❌ No.\
`volatile` gives visibility only.\
`synchronized` gives visibility + atomicity + mutual exclusion.
