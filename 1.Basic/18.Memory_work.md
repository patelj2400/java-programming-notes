# 1. How Memory Changes During Method Calls

#### Key Idea

- Every method call creates a **new stack frame**

- Stack = method execution

- Heap = objects shared across methods

---

#### Example

    public class Test {
        public static void main(String[] args)
        {
            int x = 10;
            change(x);
            System.out.println(x);
        }

        static void change(int y) {
            y = 20;
        }

    }

---

### 🧠 What happens in memory?

#### Step 1: `main()` starts

    Stack:
    main():
    x → 10

---

#### Step 2: `change(x)` is called

👉 New stack frame created

    Stack:
    change():
    y → 10 (copy of x)

    main():
    x → 10

---

#### Step 3: Inside method

y = 20;

    Stack:
    change():
    y → 20

    main():
    x → 10

---

#### Step 4: Method ends

👉 `change()` frame removed

    Stack:
    main():
    x → 10

✔ Final Output: **10**

👉 Because Java is **pass-by-value** (copy is passed)

---

# 2. Objects in Method Calls

#### Example

    class Student {
        int marks;
    }

    public class Test {
        public static void main(String[] args)
        {
            Student s = new Student();
            s.marks = 50;
            change(s);
            System.out.println(s.marks);
        }

        static void change(Student s1) {
            s1.marks = 100;
        }

    }

---

## Memory Flow

#### Step 1

    Stack:              Heap:
    s -------->         Student { marks = 50 }

---

#### Step 2: Method call

    Stack:
    change():
    s1 ----\
            → same object

    main():
    s -----/

---

#### Step 3: Modify object

    s1.marks = 100;

    Heap:
    Student { marks = 100 }

✔ Output: **100**

👉 Because both references point to **same object**

---

#### Important Trick

    static void change(Student s1) {
        s1 = new Student();
        s1.marks = 200;
    }

👉 Now:

- New object created

- But original reference unchanged

✔ Output: **50**

---

#### Summary (Method Calls)

| Case            | Result                                |
| --------------- | ------------------------------------- |
| Primitive       | Copy of value passed → no change      |
| Object          | Copy of reference → can modify object |
| Reassign object | No effect outside                     |

# 3. Interview Trick Questions: `==` vs `equals()`

---

#### Rule

| Operator   | Meaning                               |
| ---------- | ------------------------------------- |
| `==`       | Reference comparison (memory address) |
| `equals()` | Content comparison                    |

---

#### Trick 1: String Pool

    String a = "Hello";
    String b = "Hello";

    System.out.println(a == b); // true
    System.out.println(a.equals(b)); // true

✔ Same pool object

---

#### Trick 2: new String

    String a = new String("Hello");
    String b = new String("Hello");

    System.out.println(a == b); // false
    System.out.println(a.equals(b)); // true

✔ Different objects

---

#### Trick 3: Mix Case

    String a = "Hello";
    String b = new String("Hello");

    System.out.println(a == b); // false
    System.out.println(a.equals(b)); // true

---

#### Trick 4: intern()

    String a = new String("Hello");
    String b = a.intern();

    System.out.println(a == b); // false

👉 `b` → pool
👉 `a` → heap

---

#### Trick 5: Integer Cache (VERY IMPORTANT)

    Integer a = 100;
    Integer b = 100;

    System.out.println(a == b); // true

    Integer x = 200;
    Integer y = 200;

    System.out.println(x == y); // false

#### Why?

- Java caches values **-128 to 127**

- Outside → new objects

---

#### Trick 6: Custom Objects

    class A {
        int x = 10;
    }

    A a1 = new A();
    A a2 = new A();

System.out.println(a1 == a2); // false\
System.out.println(a1.equals(a2)); // false

👉 Because `equals()` not overridden

---

#### Golden Interview Line

👉 "In Java, `==` compares references, while `equals()` compares content---unless not overridden."

---

#### Final Cheat Sheet

- ✔ Java is **always pass-by-value**
- ✔ Objects → reference copied
- ✔ `==` → address
- ✔ `equals()` → content (if overridden)
- ✔ String Pool → reuse
- ✔ Integer cache → -128 to 127

# Why String is immutable (linked to String Pool)

#### What Does "Immutable" Mean?

👉 A **String object cannot be changed after it is created**

    String s = "Hello";
    s = s + " World";

⚠️ This does NOT modify `"Hello"`
👉 It creates a **new object**

---

#### Memory View (Why this matters)

##### Example:

    String s1 = "Hello";
    String s2 = "Hello";

##### Memeory flow

    Stack:          String Pool:
    s1 --------\
                --> "Hello"
    s2 --------/

👉 Only **one object** exists

---

##### Now modify:

    s1 = s1 + " World";

##### Memeory flow

    Stack:          Heap / Pool:
    s1 -------->    "Hello World" (new object)
    s2 -------->    "Hello" (unchanged)

👉 Original `"Hello"` is untouched

---

## WHY String is Immutable (Core Reasons)

#### 1. String Pool Optimization (BIGGEST REASON)

If Strings were mutable:

    String a = "Hello";
    String b = "Hello";

    a = "Hacked!";

👉 Then `b` would also change 😱

✔ That would break memory sharing

👉 Because Strings are immutable:

- Safe to **share same object**

- Saves memory

- Improves performance

---

#### 2. Security

Strings are used in:

- Passwords

- File paths

- URLs

- Database connections

Example:

    String password = "admin123";

If mutable:
👉 Someone could change it after validation

✔ Immutability ensures:

- Value cannot be altered unexpectedly

---

#### 3. Thread Safety

- Immutable objects are **automatically thread-safe**

- No synchronization needed

👉 Multiple threads can safely use same string

---

#### 4. Hashing & Performance

Strings are heavily used as keys in:

- `HashMap`

- `HashSet`

        map.put("key", value);

👉 Hashcode is cached

If String were mutable:

- Hashcode would change

- Data structure would break

---

#### 5. Caching (interning)

    String s = "Hello";

👉 JVM can reuse it from pool

✔ Works ONLY because:

- Value never changes

---

### Internal Implementation (Important)

    final class String {
        private final char[] value;
    }

👉 Key points:

- Class is `final` → cannot extend

- Internal array is `final`

- No method modifies the original data

---

### Interview-Level Explanation (Best Answer)

👉 "String is immutable to enable **String Pooling, security, thread safety, and reliable hashing**. Because Strings are shared in the pool, immutability ensures that one reference cannot affect others."

---

### Quick Comparison

| Feature          | Mutable | Immutable (String) |
| ---------------- | ------- | ------------------ |
| Change value     | ✔       | ❌                 |
| Safe sharing     | ❌      | ✔                  |
| Thread-safe      | ❌      | ✔                  |
| Pooling possible | ❌      | ✔                  |

---

    String s = "Hello";
    s.concat(" World");
    System.out.println(s);

✔ Output: `Hello`

👉 Because `concat()` returns new object, doesn't modify original

---

#### Final Visualization

    Before:
    "Hello" → shared

    After modification:
